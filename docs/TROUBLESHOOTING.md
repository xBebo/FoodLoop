# FoodLoop troubleshooting

## Database does not exist or migrations are pending

Normal application startup does not create or migrate the database. Run:

```powershell
dotnet tool restore
dotnet ef database update --project src/FoodLoop.Infrastructure --startup-project src/FoodLoop.Web -- --environment Development
```

Then run the explicit Development seed command if reference data is needed:

```powershell
dotnet run --project src/FoodLoop.Web -- --seed
```

## Demo users were not created

The seed always creates reference roles/categories, but demo users are created only when `Seed:DemoPassword` is configured privately. Do not commit that password.

## Automatic expiry appears delayed

The scheduler intentionally runs on an interval rather than on every request. The default is 60 seconds:

```json
"DonationExpiryScheduler": {
  "Enabled": true,
  "IntervalSeconds": 60
}
```

For a local demo, override `DonationExpiryScheduler__IntervalSeconds` in the process environment. Request-time Marketplace/Claim expiry checks still reject expired-by-time donations before the background worker persists `Expired`.

If expiry never runs, confirm:
- `DonationExpiryScheduler:Enabled` is true;
- the web process remains running long enough for the interval;
- the donation is exactly `Available`;
- `ExpiresAtUtc <= current UTC`;
- logs do not show a controlled concurrency warning or database exception.

A concurrency conflict ends only that run. The next run creates a fresh DI scope and re-evaluates persisted state.

## Tests cannot connect to SQL Server

Tests require SQL Server, not EF InMemory/SQLite. By default they use LocalDB. For another SQL Server set `FOODLOOP_TEST_SQLSERVER` privately. The login must be able to create and drop the disposable test database.

## HTTPS development certificate warning

If local HTTPS trust is required:

```powershell
dotnet dev-certs https --trust
```

## Login redirects or access denied

- Pending and Rejected organizations cannot log in.
- Suspended Donors cannot log in.
- Suspended Beneficiaries can log in for read-only history/profile behavior but cannot perform protected mutations.
- Admin pages require the Admin role.
- Courier task details require the assigned Courier.
- Foreign organization/claim/donation identifiers are rejected by server-side ownership checks.

## Profile update reports a concurrency conflict

The profile form carries the Organization RowVersion. If another write changes the organization first, the stale update is rejected. Reload the page to get the current RowVersion and reapply the intended Name/Address change.

## Handover verification fails

Check the implemented rules:
- the code is 64 hex characters generated by the server;
- it belongs to the same claim, assigned courier, and purpose;
- it has not expired or been consumed;
- Delivery requires persisted Pickup evidence;
- the donor/beneficiary organizations are still in an allowed state;
- the donation itself has not expired.

Regenerating a code invalidates the prior outstanding code.

## Do not troubleshoot by weakening security

Do not disable antiforgery, ownership checks, role checks, RowVersion checks, QR purpose binding, or organization-state checks to make a demo pass. Fix the underlying state/setup instead.
